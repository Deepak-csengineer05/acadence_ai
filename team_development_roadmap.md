# Acadence AI - 4-Student Team Development Roadmap

Building a project in a team of 4 requires clear division of labor to prevent merge conflicts, keep everyone active, and ensure that **each student has a distinct module to present to the evaluation committee**.

Here is how you can divide roles, schedule phases, and collaborate effectively.

---

## 1. Team Role Distribution

We recommend dividing roles based on key architectural boundaries (Frontend, Database/Auth, local NLP/Vector DB, and local LLM/Integrations):

| Student | Assigned Role | Main Responsibility | Project Viva (Presentation) Topic |
|---|---|---|---|
| **Student A** | **Frontend & UI Lead** | React SPA setup, Routing, State Management (Auth context), Custom Styling, Views (Dashboard, Admin, Upload). | "User Interface Design, Responsive State Management, and Client API Integration." |
| **Student B** | **Core Backend & DB Lead** | Database models (SQLAlchemy/SQLite), JWT Auth pipeline, CRUD API endpoints, File System uploads. | "Relational Database Schema, Token Authentication Security, and CRUD API Architecture." |
| **Student C** | **Data Parsing & Vector Search Engineer** | Text extraction from PDF/docx, text chunking, `SentenceTransformers` integration, local Qdrant DB management. | "Semantic Vector Indexes, Text Chunking, and High-Speed Embeddings Generation." |
| **Student D** | **LLM & RAG Orchestration Engineer** | Local Ollama client, Prompt Engineering, Citation/Grounding algorithm, System Health Checks, Git & CI. | "Retrieval-Augmented Generation (RAG) Architecture, Context Synthesis, and Citations Grounding." |

## 2. Phase-by-Phase Roadmap for a 4-Student Team

To prevent team members from blocking each other, development is broken down into structured, independent parallel tasks.

### Phase 1: Planning & Local Environment Verification (Days 1 - 4)
*   **Why**: Everyone must align on the API contracts and folder structures. If everyone has a different environment version, nothing will merge.
*   **Tasks & Assignments**:
    *   **Student D (Systems)**: Sets up the Git repository with a `dev` and main branch. Runs the basic folder scaffold. Researches and runs Ollama locally to verify model response.
    *   **Student A (Frontend)**: Initializes React via Vite. Sets up global CSS styling guidelines.
    *   **Student B (Backend)**: Initializes FastAPI project configuration and creates `/docs` setup.
    *   **Student C (Data)**: Installs and tests dependencies like PyPDF, docx2txt, and SentenceTransformers to ensure they run locally.

### Phase 2: Relational DB & Auth Pipeline (Days 5 - 11)
*   **Why**: Every interaction (notes upload, search, leaderboard) requires a user session and schema definition. Having this ready early gives the frontend real endpoints to integrate with.
*   **Tasks & Assignments**:
    *   **Student B (Backend)**: Designs SQLite schema (`User`, `Document`, `Course`, `Department`). Writes CRUD queries. Implements registration, login endpoints, and password hashing.
    *   **Student A (Frontend)**: Builds the login and registration UI. Implements JWT storage and state handling (context).
    *   **Student C & D (AI)**: Work offline from the database. Create the mock functions for semantic chunking and test Ollama's response times using mock text queries.

### Phase 3: Core Repo, Storage & Ingestion Pipeline (Days 12 - 18)
*   **Why**: We need files uploaded and parsed before we can build the RAG search.
*   **Tasks & Assignments**:
    *   **Student B (Backend)**: Implements file upload endpoint, file sanitization, and saves files locally into `/data/uploads`.
    *   **Student C (Data)**: Builds the ingestion pipeline: when a file is uploaded, reads the raw text, splits it into semantic chunks, and prints the result to console.
    *   **Student A (Frontend)**: Designs and builds the "Upload Resource" form UI (drag-and-drop file inputs, course dropdowns, tag inputs) and connects it to Student B's endpoint.
    *   **Student D (LLM/RAG)**: Integrates the local Qdrant collection client in python. Prepares functions to insert chunks generated by Student C into the vector database.

### Phase 4: Local RAG Integration (Days 19 - 28)
*   **Why**: The heart of the project. Here we tie the vector database search to the LLM.
*   **Tasks & Assignments**:
    *   **Student C (Data)**: Connects ingestion pipeline directly to Qdrant. Generates embeddings on-the-fly when files are approved.
    *   **Student D (LLM/RAG)**: Implements local search function. Takes a user question, gets the top chunks from Qdrant, builds the RAG prompt, sends it to Ollama, and returns the answer with metadata reference.
    *   **Student B (Backend)**: Exposes search endpoints (`/api/v1/search/semantic` and `/api/v1/search/classic`).
    *   **Student A (Frontend)**: Builds the search results interface showing standard cards (for classic metadata search).

### Phase 5: UI Integration & Interactive Chat (Days 29 - 38)
*   **Why**: Transition from simple search results to interactive AI chat panels with citations.
*   **Tasks & Assignments**:
    *   **Student A (Frontend)**: Builds the split-pane AI chat panel. Renders messages, typing status, and citations.
    *   **Student D & B**: Create streaming chat endpoints using FastAPI's `StreamingResponse` so that chatbot answers stream to Student A's UI.
    *   **Student C (Data)**: Fine-tunes chunking parameters (size vs overlap) and tests context retrieval precision.

### Phase 6: Admin Dashboard, Leaderboard & Viva Prep (Days 39 - 45)
*   **Why**: Polish and add administrative moderation. Prepare documentation for presentation.
*   **Tasks & Assignments**:
    *   **Student B & A**: Create Admin Panel backend & UI (approve uploads, review flags).
    *   **Student A & C**: Write leaderboard ranking algorithms based on upvotes. Design leaderboard UI.
    *   **Student D (Systems)**: Performs end-to-end integration tests. Packages database migrations and writes the final setup guide (`README.md`).
    *   **All Students**: Write the project report. Each writes the section corresponding to their Project Viva topic.

## 3. Why This Roadmap is Efficient (Rationale)

1.  **Loose Coupling (Parallel Work)**: The frontend (Student A) and Backend/Database (Student B) can work in parallel by agreeing on JSON schemas first. While they build the app foundation, Student C and D can test AI algorithms in standalone script environments without needing a database.
2.  **No Cloud Blockers**: By staying 100% offline (SQLite, local Qdrant, local Ollama, SentenceTransformers), you avoid cloud billing boundaries, api rate limits, and internet lag during development.
3.  **Identifiable Contributions**: When presenting to professors, "I did the UI" is often criticized as not enough coding for a CS degree. By dividing tasks this way:
    *   Student A can show complex state management and custom CSS animations.
    *   Student B can show database indexing and security.
    *   Student C can explain high-dimensional math (vector embeddings, cosine similarity search).
    *   Student D can explain prompt engineering, local model optimization, and contextual grounding.
